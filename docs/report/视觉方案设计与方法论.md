# 感知方案：设计原理与评测方法论（视觉 + 视觉-雷达融合）

> 本文阐述**为什么这样设计**——任务定义、数据选取、指标选择、对比实验、微调策略，
> 以及**视觉-雷达融合**的思路与依据。具体数字见 [`精度评测结果.md`](../精度评测结果.md)，
> 融合的完整公式/实现见 [`视觉雷达融合设计.md`](视觉雷达融合设计.md)；本文回答的是"为什么这么做、凭什么可信"。

---

## 1. 项目定位决定一切

我们做的是**电动车（非机动车）的前向视觉感知**，不是汽车 ADAS。这一条载体差异是后续所有设计决策的源头：

- 电动车**不走机动车道**，在路面、人行道边、混合交通中穿行；
- 行驶速度低、视角低、场景更杂（夜间、雨雾、逆行、行人/两轮车贴近）；
- 算力在端侧（DK-2500，Intel Core Ultra），必须**实时**。

因此我们的视觉任务被定义为两件事，并各自做了一个**有意识的简化决策**：

| 任务 | 我们的定义 | 放弃的常见做法 |
|---|---|---|
| 语义分割 | **整片路面 road** 的可行驶地面 | 车道级"可行驶区域 drivable" |
| 目标检测 | **类别无关的障碍物**（人+各类车合并） | 精细多类别检测（区分人/车/卡车…） |

下面两节解释这两个决策的理由——这正是评委最想看到的"为什么"。

---

## 2. 任务定义的设计原理

### 2.1 分割：为什么只测"整片路面"而非"可行驶车道"

- **载体不匹配车道语义**：drivable area 是为汽车定义的车道级概念，电动车根本不按车道行驶，车道线对我们意义有限；
- **"整片路面"才是电动车真正能骑的地面**，语义上更贴合风险判断（前方是不是路面、能不能走）；
- **评测更公平**：road 类在各大数据集都有干净、明确的标注，IoU 评测不受车道线粒度、标注口径差异干扰。

### 2.2 检测：为什么"类别无关"，不分人和车

这不是偷懒，而是**对电动车安全场景的正确建模**：

1. **风险不靠类别区分**：对电动车而言，撞人和撞车的风险无法简单分高低，真正决定风险的是**几何**——距离、是否挡在路径上、目标大小，类别是次要因素；
2. **小模型的分类本就不可靠**：nano 级模型 + 跨域（COCO→驾驶场景），精细分类很脆弱，把决策建立在不可靠的类别上会放大错误；
3. **顺带规避了编号对齐难题**：COCO、BDD、IDD 的类别体系互不相同，若按类别评测要做复杂且易错的映射；统一成"障碍物 vs 背景"后，两边都先筛出障碍物类再**不分类按 IoU 匹配**，干净且鲁棒。

> 我们仍保留"两轮车"这个**关注子集**单独统计 recall——因为非机动车（电动车、自行车、摩托）是本项目最该看见、最易被漏检的对象，必须单独盯住其漏检率。

## 3. 数据集选择的原理：每一个都在补一个缺口

核心思想：**单一数据集无法代表电动车要面对的世界**，所以我们用"多数据集组合 + 按集分别评测"来逼近真实泛化能力，而不是凑一个好看的平均分。

### 3.1 分割数据集（共 1004 张）

| 数据集 | 张数 | 补的缺口（为什么需要它） |
|---|---|---|
| **Cityscapes** | 200 | 经典城市街景基准，是分割模型的"主场"，作为能力上界参照 |
| **IDD**（印度） | 204 | **混合交通、非结构化道路**——最接近电动车场景（路边模糊、人车混行） |
| **ACDC** | 200 | **恶劣天气**专项：雾/雨/雪/夜各 50 张，直接压测鲁棒性 |
| **BDD100K** | 300 | 美国大规模多样驾驶，天气/时段分布广，泛化基准 |
| **CamVid** | 100 | 早期低分辨率街景，验证对不同画质的稳健性 |

**为什么必须"按数据集分别报、再按天气拆 ACDC"，而不是合并算一个平均 IoU？**
- 各集难度差异极大（Cityscapes 晴天 vs ACDC 夜间），**池化平均会掩盖短板**——而短板（夜间崩不崩）恰恰是安全关键；
- 分开报才能回答"模型在最难的夜间/雾天还能不能用"，这比一个虚高的总分有意义得多。
- 实测正是这样暴露了 PIDNet 夜间崩到 23% 而 road-adas 仍有 64% 的关键差异——若只看平均分根本看不到。

### 3.2 检测数据集（原始 2300 张）

| 数据集 | 张数 | 补的缺口 |
|---|---|---|
| **BDD100K** | 1500 | 主力：规模大、时段（白天 933 / **夜间 456**）和天气标注齐全，支撑细分分析 |
| **IDD**（印度） | 500 | **稠密混合交通、大量两轮车**，压测拥挤场景漏检 |
| **DAWN** | 300 | **真实雾天**专项，压测恶劣天气检测 |

**为什么对 BDD 做了分层抽样（883 含两轮车 + 617 随机）？**
- 两轮车在自然分布里偏少，若纯随机抽样，测试集里两轮车样本不足，**两轮车 recall 估计会非常不稳**；
- 所以我们**有意过采样含两轮车的图**来获得稳定的两轮车 recall 估计；
- 同时保留 **617 张"无两轮车"的随机图作为无偏总体**，用它估计真实场景下的整体表现——这样既盯住了关键子集，又没有让过采样污染总体结论。这一"双轨"设计是本评测可靠性的关键之一。

## 4. 评测指标的设计原理

### 4.1 分割：以 road IoU 为主

- IoU（交并比）直接衡量"预测路面"与"真实路面"的重合度，是分割的标准、公认指标；
- **统一标签空间**：各数据集 road 的标注值不同（Cityscapes=7、IDD/BDD/ACDC=0、CamVid 用颜色），我们用统一映射工具把 GT 全部归一成 `{road=1, 背景=0, 忽略=255}` 再算，**保证跨集可比**；
- **弱化像素准确率**：它会被大面积易识别区域（天空、建筑）拉高，给出虚假的乐观——不作为主指标。

### 4.2 检测：以 recall 为先，按尺寸分层

指标优先级是**按"对电动车安全的重要性"排的**，不是按惯例：

| 优先级 | 指标 | 为什么排这个位置 |
|---|---|---|
| 🥇 | **Recall@0.5** | **漏检 = 安全命门**。没看见的障碍物 = 没机会避让，这是第一位的 |
| 🥇 | **按尺寸拆（小/中/大）** | 诊断"多远能看到"。小目标 = 远处障碍 = 反应距离，nano 的短板必须量化 |
| 🥇 | **两轮车 recall** | 本项目最该看见的对象，单独盯漏检率 |
| 🥈 | Precision@0.5 | 控误报、影响可用性；但对安全，**误报远没有漏检致命** |
| 🥉 | mAP@0.5 / @.5:.95 | 跨置信度综合分，主要用于**模型间横向对比** |

> 这套优先级解释了我们如何读结果：**precision 高、recall 低的保守模型对电动车不够安全**——我们宁可多报几个框，也不能漏掉真障碍。微调正是冲着把 recall 拉起来去的。

### 4.3 指标引擎用 torchmetrics，不手写

mAP 计算细节多、极易写错（早期队友手写版已出过 bug）。改用社区公认正确的 `torchmetrics` 库，**既保证正确性又省工**——这是"结果可信"的工程保障。

## 5. 对比实验的设计原理（可靠性核心）

这一节是整套评测"靠不靠谱"的关键。我们做了五件事来保证结论站得住：

### 5.1 先立 FP32 基线，分清"精度问题"和"速度问题"

- PyTorch FP32 ≈ OpenVINO FP32（导出无损，已抽查确认一致），所以**精度只在 FP32 上评一次**即可代表模型能力；
- FP16 精度等同 FP32，无独立价值，归入端侧速度轮；INT8 的精度损失留给量化轮专门权衡；
- 这样把**"模型本身准不准"和"在板子上快不快"彻底解耦**，每一轮只回答一个问题，结论清晰不混淆。

### 5.2 防数据泄漏：训练/测试严格隔离

微调时我们坚持一条铁律：**测试用过的图，绝不进训练**。
- 本地 BDD val 10000 张，测试 manifest 用掉一部分，**剩余留出图才用于训练**；
- 我们甚至发现并主动暴露了一个隐患（见 §6.2 两轮车），宁可重切数据也不允许泄漏。
- 泄漏会让"提升"变成自欺欺人的假象——杜绝它，提升才是真的。

### 5.3 三方同台：baseline / v1 / v2 在同一测试集上比

模型升级后，我们**没有**拿"新模型的新测试集"去比"旧模型的旧分数"（那是田忌赛马式的自欺）。
而是把**原始 COCO 版、微调 v1、微调 v2 全部在同一个 v2 manifest 上重测**，确保每一栏数字都可直接对比。

### 5.4 纯泛化测试：留两个域完全不参与训练

微调只用了 BDD 的数据，**IDD（印度）和 DAWN（雾天）训练时一张都没见过**。
于是它们成了**纯泛化检验**：如果模型在没训练过的印度交通、雾天上也变好，说明它学到的是"障碍物/两轮车长什么样"的通用特征，而非死记 BDD。实测两轮车 recall 在 IDD/DAWN 上同步回升，正印证了这一点——**这比域内提升更有说服力**。

### 5.5 全程可复现

- 评测**由 manifest（CSV 清单）驱动**：评哪些图、属于哪个集/天气/时段，全部固定写死在清单里；
- 数据划分用**固定随机种子 / 确定性哈希**，任何人重跑结果一致；
- 路径与数据根**外置到配置文件**，每个人改自己的本地路径即可，互不冲突。

## 6. 微调方法论

### 6.1 为什么是"微调"而非"换更大模型"

基线评测暴露的根因是**域差**（COCO 通用域 ≠ 驾驶域），不是模型架构不行。对症的解法对比：

| 方案 | 精度 | 速度 | 是否解决域差 |
|---|---|---|---|
| 换大模型（s/m/l） | ↑ | **↓ 变慢** | 否（仍是 COCO 域） |
| 提高输入分辨率 | ↑（小目标） | ↓↓ | 否 |
| **驾驶域微调** | ↑↑ | **不变** | **是** |

微调是**唯一"精度涨、速度不掉"**的路径（模型仍是 nano），所以是端侧实时场景的最优选择。

### 6.2 单类设计 + 两轮车数据缺口的发现与修正

- **单类 obstacle**：与§2.2 的类别无关定义一致，让模型专注"有没有障碍"而非分类，小数据上更稳；
- **诚实的发现**：构建训练集时发现——BDD val 里 883 张含两轮车的图**全部被测试集占用了**，导致 v1 训练池**两轮车为 0**，模型从没见过两轮车，自然学不会；
- **主动修正（v2）**：把这 883 张**重切为 600 训 / 283 测**，并对两轮车图**过采样 ×3**补偿其稀少，重训。
- 结果两轮车 recall 翻倍且泛化同步提升（见结果文档）。**这个"发现问题→暴露→修正→验证"的闭环，本身就是方案可靠性的最好证明**。

## 7. 多传感器融合的设计原理（视觉 + 毫米波雷达）

> 完整公式、关联方法与实现见 [`视觉雷达融合设计.md`](视觉雷达融合设计.md)；本节讲**为什么这么融**。

### 7.1 为什么要加雷达：补视觉的盲区

视觉和雷达的盲区**互补**，这是融合的根本动机：

| 传感器 | 强项 | 盲区 |
|---|---|---|
| 视觉（检测+分割） | 知道「是什么」(人/车)、精确 2D 形状/位置、给出路面 | 单目**估距粗**、只认训练过的类别、暗光/遮挡退化、**有漏检** |
| 毫米波雷达（LD2451） | **真实距离/相对速度/TTC**、暗夜浓雾可用、测**任何物理回波** | 不知道「是什么」、角分辨率粗、有路边杂波 |

视觉最缺的"多远、多快"恰是雷达的强项；视觉漏掉的物理障碍，雷达能兜住。

### 7.2 融合哲学：并集保 recall + 几何门控保 precision

- **取并集，不取交集**：任一传感器看到即视为障碍物（OR 不 AND），谁也不能否决谁——守住"漏检最致命"的安全命门；
- **类别只调风险高低、不决定算不算**：与 §2.2 检测的"类别无关"一脉相承，雷达单独看到的回波就是又一个"类别未知的障碍物"；
- **几何门控压误报**：并集会引入雷达的路边杂波（护栏、路沿、停车），故所有障碍物都保留，但风险由"**在不在行进路径上 + 是否接近 + 是否在路面上**"调制。并集提 recall，几何保 precision。

### 7.3 理论主线：证据栅格的「未知」态

雷达看到、视觉没识别的目标**不丢弃**——它可能是没训练过的障碍类型（杆/栏/落物），或被漏检的人/车。
**证据占据栅格（Dempster-Shafer）** 把单元状态分为 **Free / Occupied / Unknown** 三态，
"Occupied 但 Unknown" 正是"有东西、但不知道是什么"。该框架把"不知道"建模为**独立状态而非直接丢弃**，
是我们保留"未知障碍物"的理论依据。

### 7.4 为什么是「目标级」融合，而非场景级相加

- **常见做法**：视觉给一个风险分、雷达给一个风险分，相加——两者**各算各的**，视觉仍用粗略 bbox 估距；
- **我们的做法**：按角度把雷达目标和视觉框**关联**，让每个目标用上雷达**真实距离/TTC**（视觉∩雷达）；
  视觉漏检、雷达单独看到的留作**未知障碍**；雷达看不到（如画面边缘 >15°）的退回视觉估距。产出的是**逐目标综合风险**。
- **不重复计算**：雷达已折进统一的障碍物风险 R_obs，故综合风险里**去掉独立的雷达距离项**（权重置 0）；
  同时保留**视觉失效时以纯雷达兜底**——摄像头/模型挂掉，雷达仍经 R_obs 报警，安全冗余不丢。

### 7.5 端侧实时约束塑造的取舍

- **融合层零额外推理**：只在"已算好的检测框 + 分割掩码"上做纯算术与查表，不引入第二次模型推理；
- **分割路面门控是白捡的协同**：判断雷达回波在不在路面，复用**当帧已算好的分割掩码**查表即可，几乎零延迟；
- "雷达提示视觉重检"的**重跑推理版**因延迟过大**不做**，只保留改后处理阈值的免费版（二期可选）。

### 7.6 硬件现实反哺设计

LD2451 **水平探测角仅 ±15°**——天然只看正前 30° 锥，**路边大角度杂波在硬件层面就被排除**，
让几何门控的压力小了一半。融合的角度关联、横向门控外边界都按这个真实规格设定。

## 8. 诚实的局限（写进报告反而加分）

主动声明局限，体现的是科学态度而非心虚：

- **视角域差**：现有公开数据都是**汽车视角**，尚无电动车第一视角自采数据。本轮分数代表"汽车域"能力，电动车低视角表现需后续自采补齐 + 定性目检；
- **微调数据规模有限**：仅用 BDD 留出图，两轮车训练样本仅 600 张；取 BDD100k train 全量可进一步提升；
- **未含 INT8 与端侧延迟**：量化精度损失、CPU/iGPU/NPU 实测速度属后续专门轮次；
- **融合参数未标定**：相机 FOV、雷达-相机角度对齐、速度方向等需上硬件标定；本轮融合逻辑用合理默认值，已在 mock 与协议示例上验证、尚无真实雷达数据。

---

## 9. 一句话总结思路

> **从电动车这一载体出发**，把任务**正确地简化**为"整片路面 + 类别无关障碍物"；用**多数据集组合 + 按集/天气/尺寸分层**逼近真实泛化，用**recall 优先**对齐安全目标；通过**FP32 基线解耦、防泄漏留出、同台三方对比、纯泛化检验、全程 manifest 可复现**保证结论可信；用**对症的域内微调**在不牺牲速度的前提下补齐短板；再用**视觉-雷达目标级融合**（并集保 recall、几何门控保 precision、未知障碍不丢、雷达兜底视觉失效）把"是什么"与"多远多快"互补成统一的障碍物风险，并诚实记录边界。

每一步都能回答"为什么这么做"——这就是本方案的思路与可靠性所在。
