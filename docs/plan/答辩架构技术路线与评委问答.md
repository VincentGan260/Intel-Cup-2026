# RiderGuardian 答辩架构、技术路线与评委问答

> 适用场景：赛前答辩复习、队员统一口径、评委追问准备。
>
> 当前口径：项目最终主线为“规则风险模型 / 规则风险网络 + 雷达快速 TTC 通道 + 视觉场景理解 + Dashboard/马达/云端闭环”。不要再把 GT-MRFN 作为当前最终主风险判断主线来讲；如需提及，只作为前期探索或后续可扩展训练链路。

## 1. 项目一句话定位

RiderGuardian 是一个面向骑行场景的前向安全预警原型系统。系统使用 Intel DK2500 作为边缘计算平台，接入前向摄像头、HLK-LD2451 毫米波雷达和可选 GPS，通过雷达 TTC 规则、视觉目标检测、道路语义分割、风险状态仲裁、震动马达提醒、Web Dashboard 和云端数据留存，实现“感知-判断-提醒-记录-回放”的完整闭环。

对外表述时要强调：

- 这是骑行辅助提醒系统，不是自动驾驶系统。
- 当前系统不做自动制动，不声称完成安全认证。
- 风险等级是提醒等级，不是事故概率。
- 规则风险模型是可解释主线，视觉深度学习用于感知，不直接黑盒决定最终安全等级。

## 2. 当前最终技术路线

系统最终技术路线可以概括为：

```text
前向摄像头 + 毫米波雷达
        |
        |-- 雷达快速通道：距离 / 角度 / 相对速度 -> 前向门控 -> TTC -> 风险等级
        |
        |-- 视觉理解通道：YOLO 障碍物检测 + 道路语义分割 -> 场景证据
        |
        |-- 状态仲裁：雷达事件 + 视觉事件 -> warning_level / reason / evidence
        |
        |-- 输出闭环：Dashboard + 震动马达 + 本地日志 + 云端同步
```

设计原则：

- 雷达负责低延迟紧急提醒。
- 视觉负责场景理解、障碍物证据和道路区域证据。
- GPS 是可选模态，失效时记录 `gps.valid=false`，不阻塞核心功能。
- 传感器异常不能伪装为低风险，应进入 `unknown` 或 `degraded`。
- 所有记录使用统一 `monotonic_ns` 时间轴，保证可追溯。

## 3. 运行架构

### 3.1 主入口

主要入口文件：

- `start_collection.py`：外采 / 测试采集入口，会记录本地数据。
- `start_demo.py`：最终演示入口，不写训练数据，适合答辩展示。
- `run_dashboard.py`：底层统一启动入口，负责初始化摄像头、雷达、GPS、视觉、规则、马达、Dashboard、云端同步等模块。

答辩时可以说：

> 我们把采集模式和演示模式拆成两个一键入口，底层复用同一套真实感知和推理链路。采集模式打开 Recorder，演示模式关闭本地训练数据写盘，便于现场稳定演示。

### 3.2 线程与数据流

当前系统不是单线程顺序处理，而是多条异步链路：

```text
CameraFrameProducer
  - 后台持续读取摄像头最新帧
  - Dashboard、视觉推理、Recorder 共享同一帧缓存

RadarWorker
  - 独立读取 LD2451
  - 独立计算雷达 TTC 风险事件
  - 高风险不等待视觉

VisionWorker
  - 从相机缓存取最新帧
  - 顺序执行检测和分割
  - 输出视觉证据和视觉事件

StateLoop
  - 约 5 Hz 汇总当前状态
  - 写入 DashboardStateStore
  - 记录 samples.jsonl
  - 可选发布云端样本

FastAPI Server
  - 提供 Dashboard 页面
  - 提供 /api/state
  - 提供视频流
```

核心优势：

- 雷达快速通道不会被视觉推理阻塞。
- 摄像头只被一个后台线程读取，避免多个消费者争抢 `/dev/video0`。
- Dashboard 展示频率和雷达安全判断频率解耦。

## 4. 视觉链路说明

### 4.1 当前视觉模型

当前视觉链路：

```text
摄像头帧
  -> YOLO26n_v2 INT8 目标检测 @ OpenVINO NPU
  -> road-segmentation-adas FP16 道路分割 @ OpenVINO GPU
  -> VisionData
```

实测延迟大致为：

```text
检测：约 21 ms
分割：约 114 ms
总视觉链路：约 135 ms
```

### 4.2 为什么 NPU + GPU 仍然是串行

需要特别注意：当前系统是“异构部署”，不是“检测和分割并行执行”。

虽然检测跑在 NPU，分割跑在 GPU，但当前代码是在同一个视觉处理流程中顺序执行：

```text
先检测，再分割，所以总延迟约等于两者相加。
```

评委如果问“为什么不是并行”，回答：

> 当前版本优先保证工程稳定和同帧一致性。检测和分割都消费同一帧，串行处理能保证检测框和分割 mask 严格对应同一画面。后续可以使用 OpenVINO 异步 infer request，把检测和分割放到两个线程中并行执行，再通过 frame_id 汇合，理论端到端延迟可以从两者相加优化到接近较慢一路。

### 4.3 视觉模块职责边界

视觉当前用于：

- 检测障碍物框、置信度和数量。
- 分割可行驶区域，计算可行驶区域比例。
- 为 Dashboard 提供场景解释。
- 为数据记录提供后续复盘证据。

视觉当前不用于：

- 单独触发高风险。
- 覆盖雷达高风险。
- 通过单帧框面积估算真实距离。
- 声称已经和雷达目标完成精确一一对应。

推荐答辩表述：

> 当前系统中，视觉是场景理解通道，雷达是快速安全通道。视觉帮助解释“前方是什么、路面在哪里”，雷达负责“目标离我多远、是否接近、还有多少 TTC”。

## 5. 雷达快速风险规则

### 5.1 雷达数据来源

雷达使用 HLK-LD2451，通过串口读取数据帧。

解析得到：

- 目标距离 `distance_m`
- 目标角度 `angle_deg`
- 目标相对速度 `relative_speed_mps`
- 目标信噪比 / 置信度近似值
- 最近目标距离
- 最小 TTC

项目中已经做过：

- 256000 波特率实测。
- 前向安装方向码确认。
- 角度符号统一为左负右正。
- 每次消费时排空积压旧帧，只保留最新完整帧。

### 5.2 为什么雷达优先

雷达通道比视觉更适合做紧急提醒，因为它直接提供：

- 距离
- 相对速度
- 接近 / 远离趋势

视觉虽然能识别障碍物，但单目视觉对距离和相对速度估计不稳定。因此当前系统设计为：

```text
雷达负责实时 TTC 紧急提醒
视觉负责场景证据和辅助解释
```

### 5.3 前向点目标门控

雷达目标进入风险判断前，先计算目标相对车体中心的横向位置：

```text
x_bike = radar_mount_x + distance * sin(angle)
```

当前参数：

```text
radar_mount_x = -0.055 m
point_gate_half_width = 0.36 m
```

门控条件：

```text
|x_bike| <= 0.36 m
```

0.36 m 来源：

```text
车体半宽 0.33 m
+ 工程余量 0.025 m
+ 安装测量不确定度 0.005 m
= 0.36 m
```

答辩必须说清楚：

- 这是最小点目标前向门控。
- 它不是完整碰撞包络。
- 它不是 LD2451 横向测量精度。
- 它用于过滤明显在车体侧方的目标。

### 5.4 TTC 风险判断

项目约定：

```text
relative_speed_mps < 0：目标接近
relative_speed_mps = 0：相对距离基本不变
relative_speed_mps > 0：目标远离
```

接近速度：

```text
closing_speed = -relative_speed_mps
```

TTC：

```text
TTC = distance / closing_speed
```

风险等级：

```text
low:
  没有有效接近目标进入前向门控

mid:
  有有效接近目标进入前向门控，但 TTC 还未进入紧急参考区

high:
  TTC <= urgent_ttc_s

unknown:
  雷达帧无效、过期、解析异常或全部目标异常
```

紧急参考线：

```text
urgent_ttc_s = 2.5 s + radar_to_motor_p95_s
```

其中 2.5 s 是骑行反应时间参考，不是停车距离，不是安全认证阈值。

### 5.5 unknown 为什么重要

必须区分：

```text
雷达正常报告无目标 -> low
雷达无效 / 过期 / 解析失败 -> unknown
```

答辩表述：

> 传感器坏了不能当成安全。我们把雷达异常明确标为 unknown 或 degraded，而不是降成 low，这样能避免系统在失去关键传感器时给出虚假的安全感。

## 6. 风险状态仲裁

当前系统不是简单加权平均，而是事件仲裁。

输入：

- 雷达事件：来自 TTC 快速规则。
- 视觉事件：来自障碍物和道路场景理解。

输出：

- `warning_level`
- `risk_status`
- `warning_reason`
- `evidence_sources`
- `radar_level`
- `vision_level`

原则：

- 雷达 high 优先，不等待视觉。
- 视觉可提供辅助证据，但不压制雷达高风险。
- 降级有 release hold 防抖，避免等级频繁跳变。
- 传感器失效以 `unknown/degraded` 显示。

## 7. 马达提醒策略

马达输出不是自动控制，只是骑手提醒。

```text
level 0 / low:
  静默

level 1 / mid:
  短促震动，提醒注意

level 2 / high:
  强提醒 / 持续震动，提示紧急

unknown:
  不伪装成低风险，可单独显示故障或不可判断状态
```

答辩强调：

> 我们不控制车辆制动，只通过触觉反馈提醒骑手注意前向风险。

## 8. GPS 处理策略

GPS 当前无法稳定搜星，因此系统已降级为可选模态。

实现策略：

- GPS 串口可读则读取 NMEA。
- 只有 `fix_quality > 0` 且 RMC `status=A` 才标记有效。
- 无定位时记录 `gps.valid=false`。
- 不阻塞采集、Dashboard 和雷达风险判断。

为什么不用 GPS 也能测速：

- GPS 测的是本车地面速度。
- 雷达测的是目标相对速度。
- 当前前向 TTC 规则主要依赖目标距离和相对速度，因此不依赖 GPS。

答辩表述：

> GPS 缺失会影响路线记录和本车速度分析，但不会影响当前雷达 TTC 快速预警主链路。

## 9. 时间同步与数据记录

### 9.1 时间轴

系统使用 `monotonic_ns` 作为统一同步时间轴。

原因：

- `wall_time` 可能受系统时间校准影响。
- `monotonic_ns` 单调递增，适合计算延迟和同步差。

记录字段包括：

```text
frame_capture_monotonic_ns
radar_sample_monotonic_ns
gps_sample_monotonic_ns
vision_start_monotonic_ns
vision_finish_monotonic_ns
risk_decision_monotonic_ns
motor_command_monotonic_ns
record_write_monotonic_ns
radar_delta_ms
gps_delta_ms
vision_latency_ms
end_to_end_latency_ms
```

### 9.2 Recorder 保存内容

每个 session 保存：

- `session.json`：元数据、模型路径、配置、commit、hash。
- `samples.jsonl`：逐帧结构化样本。
- `events.jsonl`：事件标签。
- `frames/`：原始帧图像。
- `quality_report.json`：自动质量检查结果。

每条样本保存：

- 原图路径
- 雷达目标列表
- GPS 有效性
- 视觉检测结果
- 道路分割特征
- 视觉雷达关联结果
- 风险决策
- 完整时间戳

## 10. 数据、训练与当前模型口径

当前答辩主风险判断是规则风险模型，不要把多模态神经网络作为最终主线。

可以这样说：

> 我们保留了结构化数据记录和窗口化训练能力，但当前答辩版本把可解释规则风险模型作为主风险判断核心。这样更适合小样本、受控场景和安全边界明确的比赛原型。

如果评委问“为什么不用神经网络直接判断风险”，回答：

> 当前真实数据规模有限，直接训练黑盒风险网络容易过拟合，也难解释。我们选择先用物理含义明确的雷达 TTC 规则作为安全主线，视觉深度学习负责感知，后续数据量足够后再把结构化特征训练模型作为辅助。

## 11. 异构部署说明

当前部署：

```text
目标检测：YOLO26n_v2 INT8 @ OpenVINO NPU
道路分割：road-segmentation-adas FP16 @ OpenVINO GPU
```

曾经遇到的问题：

```text
Invalid NPU 'device=npu'. Install 'torch_npu'
```

原因：

- Ultralytics `predict(device="npu")` 会把 NPU 理解为 PyTorch / Ascend 设备。
- DK2500 使用的是 Intel OpenVINO NPU，不是 `torch_npu`。

修复：

```python
import openvino as ov
core = ov.Core()
compiled = core.compile_model(model, "NPU")
```

答辩表述：

> 我们区分了 PyTorch 设备语义和 OpenVINO 设备语义，最终使用 OpenVINO 原生 API 把 INT8 检测模型部署到 Intel NPU。

## 12. 云端与数据库接口

当前系统提供 `CloudSyncClient`：

- 以固定频率上传精简骑行状态。
- 将无效 GPS 表示为 null。
- 将雷达无目标的 `-1` 转换为云端 schema 中的 null。
- 记录和上传短视频片段。
- 上传失败时保留本地 spool，避免数据直接丢失。

答辩时可以说：

> 云端部分不是风险判断主链路，而是用于数据留存、远程回放和后续数据库展示。

## 13. 当前系统边界

一定不要夸大：

- 不声称自动驾驶。
- 不声称自动制动。
- 不声称安全认证。
- 不声称视觉雷达已经完成精确外参融合。
- 不声称 TTC 是停车安全距离。
- 不声称当前小样本规则/数据能泛化所有道路。
- 不声称 GPS 已可靠工作。

推荐总表述：

> 当前系统是面向比赛演示和受控场景验证的骑行辅助预警原型。我们重点实现了实时感知、可解释风险判断、触觉提醒、前端展示和数据闭环，而不是宣称达到量产级安全系统。

## 14. 评委高频问题与回答

### Q1：为什么视觉检测和分割用了 NPU/GPU 还要 135 ms，不应该并行吗？

A：当前是异构串行部署，不是并行执行。检测模型在 NPU 上约 21 ms，分割模型在 GPU 上约 114 ms，但代码中为了保证同帧一致性和工程稳定，先检测再分割，所以总延迟接近两者相加。后续可以用 OpenVINO 异步 infer request 做并行，理论上把视觉端到端延迟优化到接近较慢一路。

### Q2：为什么不用神经网络直接输出风险？

A：当前真实数据量有限，直接用黑盒网络判断风险容易过拟合且难解释。我们采用规则风险模型作为主线，雷达 TTC 有明确物理意义；视觉网络负责感知，而不是直接决定安全等级。

### Q3：TTC 是什么？

A：TTC 是 Time To Collision，即在当前相对运动保持不变的假设下，目标与骑行者发生冲突的剩余时间。计算方式是距离除以接近速度。它是紧急提醒参考，不是刹车安全距离。

### Q4：2.5 秒阈值是怎么来的？

A：2.5 秒是骑行/交通设计中常见的感知-反应时间参考。我们没有把它解释为本车制动能力，也没有声称它能保证停车，只把它作为紧急提醒参考线。

### Q5：雷达误检怎么办？

A：我们加入了多层过滤：雷达帧有效性、样本新鲜度、距离范围、角度范围、接近速度、前向点目标门控。异常帧进入 unknown；异常目标会被丢弃；无目标和雷达失效严格区分。

### Q6：为什么视觉不压制雷达 high？

A：因为视觉可能受光照、遮挡、推理延迟影响。安全提醒主链路应优先保证低延迟和稳定性。雷达 high 表示 TTC 已进入紧急参考区，视觉不能因为没检测到目标就取消雷达预警。

### Q7：GPS 坏了系统还能工作吗？

A：能。GPS 是可选模态，失效时记录 `gps.valid=false`。主风险判断依赖雷达距离和相对速度，视觉负责场景证据。GPS 缺失影响路线和本车速度记录，但不影响前向 TTC 预警主链路。

### Q8：雷达测的是谁的速度？

A：雷达测的是目标相对本车的速度，不是本车绝对速度。对于 TTC 来说，相对速度正是关键输入，因为我们关心目标是否正在接近以及多久进入冲突区域。

### Q9：视觉和雷达有没有精确融合？

A：当前实现了统一时间戳和初步关联，用于展示和数据留存。但精确目标级融合需要相机内参、雷达外参、多目标关联验证。当前答辩中我们只称为辅助关联，不夸大为精确融合。

### Q10：为什么要保存原图，训练又不用原图？

A：训练/规则使用结构化特征更轻量，也更适合端侧和小样本。但保留原图可以用于复查、重新推理、修正检测结果和后续扩充数据集。

### Q11：传感器数据怎么同步？

A：所有传感器记录同一主机的 `monotonic_ns`。相机是主时间线，雷达/GPS保存实际样本到达时间，视觉保存推理开始和结束时间。质量报告会检查时间单调、同步差和延迟。

### Q12：如果雷达掉线会显示低风险吗？

A：不会。雷达掉线、帧过期或解析失败会进入 unknown/degraded，不会伪装成 low。只有雷达正常报告无目标，才是 low。

### Q13：你们的风险等级是概率吗？

A：不是。low/mid/high 是提醒等级。规则风险模型输出的是解释性等级，不是事故概率。Dashboard 中如果有分数，也只是显示用的风险索引，不能解释为事故发生概率。

### Q14：系统怎么避免视觉延迟影响安全提醒？

A：雷达有独立 `RadarWorker` 快速通道，读取雷达后立即计算 TTC 并发布雷达事件；视觉在独立线程中运行。高风险雷达事件不等待视觉结果。

### Q15：为什么用 OpenVINO？

A：DK2500 是 Intel 平台，OpenVINO 可以统一调度 CPU、GPU、NPU。我们用 INT8 检测模型部署到 NPU，用 FP16 分割模型部署到 GPU，提升端侧实时性并降低 CPU 压力。

### Q16：如果 NPU 不可用怎么办？

A：系统可以显式降级到 GPU/CPU，并在日志和 session 元数据中记录实际运行设备。我们不会把回退运行伪装成 NPU 成功。

### Q17：马达提醒是否会影响骑行安全？

A：马达只是触觉提醒，不直接控制车辆。低风险静默，中风险短促提醒，高风险强提醒。最终行为仍由骑手决策。

### Q18：为什么不接 IMU？

A：当前版本取消 IMU，是为了减少不可靠模态和接线复杂度，把重点放在雷达、视觉和规则预警闭环。系统设计中保留 valid mask 思路，未来可以重新接入。

### Q19：如何证明系统能复现？

A：每次采集都会保存 session 元数据、模型路径、模型 hash、配置 hash、git commit、逐样本时间戳和质量报告。这样可以追溯当时使用的模型、配置和数据。

### Q20：最大不足是什么？

A：当前主要不足是视觉雷达尚未完成严格外参标定，GPS 失效，数据量仍偏小，规则阈值只适用于当前原型和受控场景。后续工作是补 GPS/本车速度、完成外参标定、扩充数据并验证不同场景。

## 15. 答辩推荐讲法

建议按下面顺序讲，不要从代码开始：

1. 场景痛点：骑行前向障碍物风险提醒。
2. 系统方案：雷达快速 TTC + 视觉理解 + 触觉提醒 + Dashboard。
3. 硬件平台：DK2500、摄像头、LD2451、马达、可选 GPS。
4. 视觉部署：检测 NPU、分割 GPU，当前串行 135 ms。
5. 风险模型：前向门控 + TTC + unknown 状态。
6. 工程闭环：一键启动、实时前端、数据记录、质量检查、云端留存。
7. 边界说明：不是自动制动，不夸大安全认证。
8. 演示：正常、接近、紧急三类场景。

## 16. 一分钟压缩版

如果只给一分钟，可以这样讲：

> 我们的系统是面向骑行场景的前向安全预警原型。硬件上使用 DK2500、前向摄像头和 LD2451 毫米波雷达。软件上采用雷达快速 TTC 规则作为主风险判断，视觉使用 YOLO26n_v2 INT8 在 NPU 上检测障碍物，road-segmentation-adas FP16 在 GPU 上分割可行驶区域。雷达线程独立运行，高风险不等待视觉；视觉负责场景解释和证据留存。系统使用统一 monotonic 时间戳记录相机、雷达、视觉、风险决策和马达命令，支持 Dashboard 展示、本地记录和云端上传。当前系统定位为骑行辅助提醒，不做自动制动，也不声称安全认证。
