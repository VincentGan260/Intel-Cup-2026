# RiderGuardian 1 天冲刺 TODO

> **唯一目标**：在一天内用真实/受控数据训练出可运行的 GT-MRFN，并打通“传感器 → 风险融合 → 震动预警 → Dashboard/日志”演示闭环。
>
> **范围约束**：功能演示表 1～11 项全部实现，每项至少有一条可重复的现场演示或日志证据。一天内只缩小数据规模和工程完善度，不删功能项。

## 验收底线

- [ ] 至少有一批真实同步采集数据，高风险数据来自低速受控场景。
- [ ] GT-MRFN 用当天数据完成真实训练，保存权重、标准化参数和评估结果。
- [ ] 模型能输出 low/mid/high 概率与风险分数。
- [ ] 端侧运行 `R_final = max(R_model, R_rule)`，模型失效时可退回规则。
- [ ] 三个受控场景能触发对应风险等级、马达和日志。

## 三人分工

### 阶段 1：三人共同获取数据（B 总负责）

> 数据是共同关键路径，不是 B 一人的任务。B 负责组织、命名、完整性检查和最终交付，A/C 必须参与采集和复核。

| 人员 | 共同采集期职责 |
|---|---|
| **B（总负责）** | 硬件连接、录制启停、场景编号、时间戳/丢帧检查，汇总原始数据 |
| **A** | 现场检查特征是否齐全，确认标签边界，避免采完才发现数据无法训练 |
| **C** | 操作受控目标/录制视频，同时检查 Dashboard 与日志能否重放场景 |

**共同交付**：低/中/高风险原始片段、场景清单、首批可训练数据。完成后立即转入三路并行，不再全员继续扩充数据。

### 阶段 2：三条独立并行线

| 人员 | 独立主线 | 交付物 |
|---|---|---|
| **A：数据与模型线** | 切样本、标签/划分、GT-MRFN 训练、导出 | `samples.npz`、`split.json`、权重、特征配置、评估结果 |
| **B：硬件与端侧闭环线** | 同步、模型推理接口、规则兜底、分级马达、DK2500 设备验证 | 功能表 1/5/6/7/8 的运行日志和真实闭环 |
| **C：展示与留存线** | 视觉画面、Dashboard/WebSocket、本地日志、高风险视频、openGauss | 功能表 2/3/4/9/10 的网页和回溯证据 |

### 并行接口约定（禁止相互等待）

- T+0.5h 前冻结 `feature_schema` 和模型输出 `{probabilities, model_score, model_level}`。
- A 在真实数据整理期用合成数据开发训练程序；不等全部数据。
- B 用固定 mock 模型输出开发 ring buffer 和 `max(model, rule)`；不等 A 的权重。
- C 从 `SystemState` 固定字段开发 Dashboard/存储；不等 B 的真机联调。
- A 只向共享交付目录发布版本化模型包；B 按约定替换，不临时改接口。

## 小时级安排

### T+0～2h：三人共同首采，同时锁定接口

- [ ] A 在 30 min 内固定特征顺序、`N=5`、`X/y/group_id` 和模型输出，然后加入采集。
- [ ] B 组织设备检查和录制，统一场景编号与文件命名。
- [ ] C 负责受控目标与演示录像，同时查看 Dashboard/日志数据。
- [ ] 三人共同完成正常行驶、障碍接近、急停/横穿的首批片段并现场抽查回放。

**2h 止损线**：必须结束全员采集。某路仍不可用则带 valid=0 进入三路并行；后续补采只由 B 在必要时进行。

### T+2～6h：三路独立并行

**A：数据与模型**

- [ ] 用现有 `RiskModel` 产生初始标签，人工重点复核中/高风险和阈值边界。
- [ ] 按原始片段 `group_id` 做 7:2:1 划分，严禁同一片段的相邻窗口跨集合。

- [ ] 完成特征向量化、训练集 mu/σ 标准化和 valid 位处理。
- [ ] 实现极简 GT-MRFN：单模态小 MLP + 2 层 TCN + 门控融合 + 三分类头。
- [ ] 用合成数据先验证前向、反传、保存和重载，再替换真实数据。

**B：硬件与端侧闭环**

- [ ] 用 mock 概率实现 ring buffer、`R_final=max(R_model,R_rule)` 和异常回退。
- [ ] 保证规则风险、分级震动和 CSV 日志仍可独立运行。
- [ ] 运行 DK2500 preflight，记录 GPU/NPU 和模型编译结果。

**C：展示与留存**

- [ ] 打通真实 `SystemState` → Dashboard/日志。
- [ ] 建 openGauss 三表与最小批量上传客户端。
- [ ] 将前端 HTTP 轮询换成 WebSocket，断开 2 s 后重连。
- [ ] 实现内存帧缓冲；高风险时保存事件前后小片段并记录路径。

### T+6～9h：训练、接入与展示各自收口

- [ ] A 使用加权交叉熵，`Adam(lr=1e-3)`，batch 32/64，最多 50 epoch，early stopping=8。
- [ ] 训练时随机屏蔽单路模态，并同步把对应 valid 位置 0。
- [ ] 保存 best checkpoint、特征顺序、mu/σ、数据划分和 confusion matrix。
- [ ] 只做一次主训练 + 一次必要修正；不做大规模调参。
- [ ] B 完成端侧接入和实际设备回退，期间一直用 mock 模型包测试。
- [ ] C 完成 Dashboard、WebSocket、视频和 openGauss 各自独立验收。

**7h 止损线**：模型效果一般也立即进入部署，依靠 `max(model, rule)` 保证安全下限。

### T+9～10h：唯一集成窗口

- [ ] 校验 PyTorch 与 ONNX/OpenVINO 同一输入的概率输出近似。
- [ ] 实现 N=5 时序 ring buffer；冷启动期间用复制帧或规则风险。

## 模型最小约束

- 不允许用随机权重或纯规则冒充已训练网络。
- 特征顺序、标准化、缺失填充和 valid 位必须由训练/部署共用同一份配置。
- 报告中的样本数、准确率、召回率和延迟只写真实测量值。
- 小样本结果只表述为“原型/受控场景验证”，不宣称已证明泛化能力。

## 必要降级（不取消网络训练）

1. 数据少：缩小场景和样本量，但保留真实采集、独立片段划分和人工复核。
2. 模型不稳：缩小隐藏层/时序窗口，但保留 TCN、门控和三分类输出。
3. IR 转换卡住：先部署 ONNX Runtime/PyTorch CPU 保证真模型闭环，随后再补 OpenVINO IR。
4. NPU 不可用：视觉退 GPU/CPU/AUTO；GT-MRFN 仍用 CPU。
5. 时间不足：不删演示表功能；只将 openGauss 收缩为三表+单批上传，视频回溯收缩为单个高风险事件片段，异构调度收缩为设备绑定+回退日志。
