# 上车实测风险规则调参操作手册

本文给现场调试人员使用。目标不是一次找出“最优参数”，而是在安全、可复现的条件下，把当前理论初值逐项改成有实测依据的工程参数。

当前规则配置：`configs/warning_rules.yaml`  
当前状态：`estimated_from_stationary_risk_pending_measurement`  
理论说明：`docs/plan/IMU横向失稳风险理论与标定方法.md`

## 1. 先记住四条规则

1. 每轮只改一个参数或一条判断，其他参数保持不变。
2. 每个场景至少重复3次，关键危险场景建议5次。
3. 不做故意碰撞、无人保护摔车和高速极限动作；快速侧倾必须低速、有人扶车并有保护人员。
4. 没有稳定改善就回退，不为了“看起来更灵敏”同时放宽多个阈值。

当前融合方式是雷达、视觉、IMU对有效风险执行`max`仲裁。GPS只提供上下文，不能否决其他模态。调参时不要增加模态权重，也不要改成求平均。

## 2. 参数分级

### 2.1 第一轮必须标定

| 顺序 | 参数 | 当前值 | 主要解决的问题 |
|---:|---|---:|---|
| 1 | `configured_warning_range_m` | `100.0 m` | 当前取LD2451默认最大范围，必须与APP完全一致 |
| 2 | `imu.roll_offset_deg` | `-12.44°`（反推临时值） | 必须用本次安装的静止均值替换 |
| 3 | `imu.turn_sign` | `-1` | 确认左右转弯补偿方向没有写反 |
| 4 | 视觉走廊与`path_policy` | `center` | 减少路边目标误报，同时保留切入目标 |
| 5 | `point_gate_lateral_margin_m` | `0.025 m` | 平衡雷达路径边缘漏报和路边误报 |
| 6 | `urgent_reference_s` | `2.5 s` | 调整高风险预警提前量 |
| 7 | IMU中高风险边界 | 见第6节 | 区分正常转弯和横向失稳趋势 |
| 8 | `release_hold_ms` | `500 ms` | 抑制风险解除时的等级抖动 |

### 2.2 有余力再标定

| 参数 | 当前值 | 何时才需要动 |
|---|---:|---|
| `attention_reference_s` | `4.0 s` | 中风险明显过早或过晚 |
| 视觉`near_bottom_ratio` | `0.61` | 视觉单帧远近判断明显不合理 |
| 视觉`very_near_bottom_ratio` | `0.82` | 非常近目标边界明显不合理 |
| 视觉`attention_tau_s/urgent_tau_s` | `4.0/2.5 s` | 跟踪稳定但视觉动态预警早晚不合适 |
| GPS速度修正 | `5~30 km/h`、上限`1.25` | 雷达、视觉基础规则稳定后再做 |
| 各模态`stale_ms` | 当前配置值 | 已统计真实更新周期和线程抖动P95/P99 |

### 2.3 第一轮禁止随意修改

- `score_contract`中的`0.35/0.70`等级边界。
- `body_width_m=0.66`，除非重新测量车辆实际宽度。
- `mounting_offset_m=-0.055`和`mounting_uncertainty_m=0.005`，除非重新测量安装位置。
- `gravity_mps2=9.80665`。
- 雷达速度正负语义、协议解析和距离单位。
- `max`仲裁、风险立即升级、只延迟下降的设计。
- 检测模型、分割模型和NPU/GPU并行方案。

## 3. 测试前准备

### 3.1 固定硬件

- 摄像头、雷达、IMU必须刚性固定；测试中途不得改变角度或位置。
- 记录摄像头高度、俯仰角，雷达横向偏移和IMU安装方向。
- 核对LD2451 APP的检测范围，并把同一个数值传给Dashboard。
- 更换IMU位置、USB口或固定方式后，重新测零偏和方向。

### 3.2 运行硬件预检

在DK2500项目根目录运行：

```bash
python scripts/preflight_dk2500.py --profile dk2500 --loops 30 --vision
```

必须确认：

- 雷达、GPS、IMU连续输出有效数据。
- IMU约100 Hz，坏校验帧没有持续增加。
- 视觉模型成功初始化。
- 各设备时间戳没有未来时间、倒序或明显停滞。

### 3.3 先关闭真实马达

第一轮使用`--motor-mode off`。确认规则不会异常触发后，再用`mock`观察马达指令；最后才使用真实马达，并由专人确认振动不会影响控车。

## 4. 建立不可变基线

### 4.1 保存基线配置

```bash
cp configs/warning_rules.yaml configs/warning_rules_vehicle_baseline.yaml
```

Windows PowerShell使用：

```powershell
Copy-Item configs/warning_rules.yaml configs/warning_rules_vehicle_baseline.yaml
```

禁止直接覆盖这份基线。

### 4.2 启动整机录制

当前共享配置使用`100 m`。如果LD2451 APP不是该值，把下面的`100`替换成APP实际设置的检测范围：

```bash
python run_dashboard.py \
  --dashboard-mode real \
  --profile dk2500 \
  --enable-risk-rule \
  --enable-vision \
  --enable-imu \
  --motor-mode off \
  --configured-warning-range-m 100 \
  --record \
  --scene vehicle_baseline \
  --operator TEAM_MEMBER \
  --route CONTROLLED_ROUTE
```

每个独立参数版本使用不同的`--scene`，例如：

```text
imu_baseline
imu_attention_8deg
vision_center
vision_two_of_three
radar_margin_015
urgent_30s
release_700ms
```

### 4.3 每次录制后做质量检查

```bash
python scripts/check_dashboard_recording.py data/recordings/SESSION_DIR
```

只有`quality_report.json`通过后，该次结果才能用于调参。失败时先修复丢帧、时间戳或设备连接，不得用调阈值掩盖数据问题。

### 4.4 当前回放工具的限制

`scripts/replay_warning_session.py`可以验证：

- 时间戳和下降保持行为。
- 已记录风险事件的重新仲裁。
- 雷达、视觉、GPS、IMU故障注入。

它目前不会根据新YAML完整重算已经记录的视觉和IMU风险事件。因此，现阶段不能只更换配置回放就宣称某个阈值更好。参数比较必须使用同一路线、同一场景、单参数修改后的重新实测。原始录制仍要保留，后续补齐离线重算工具后可再次使用。

## 5. 固定测试场景

按照下列顺序进行。每段开始和结束至少保持3秒稳定状态。

| 编号 | 场景 | 期望 |
|---:|---|---|
| S01 | 静止60秒 | 无持续中高风险，测IMU零偏和设备抖动 |
| S02 | 空旷直线低/中速骑行 | 不出现持续中高风险 |
| S03 | 左右普通转弯，至少两种速度和半径 | IMU转弯补偿后不报高风险 |
| S04 | 正前目标由远及近，保持可安全停止距离 | 风险连续上升，高风险有提前量 |
| S05 | 目标从路径边缘缓慢切入 | 不漏掉路径边缘目标 |
| S06 | 路边护栏、路沿、停放车辆旁经过 | 不出现持续中高风险 |
| S07 | 宽路、窄路和缓弯 | 视觉走廊不因道路宽度产生明显误判 |
| S08 | 夜间或弱光目标 | 视觉失效时雷达仍可独立预警 |
| S09 | 雷达无目标、视觉检测到路径障碍 | 视觉风险可以独立输出 |
| S10 | 有人扶车的快速侧倾并立即恢复 | IMU在恢复前识别外倾趋势，不等倒地 |
| S11 | 小颠簸、减速和停车 | IMU不因单次冲击误报高风险 |
| S12 | 逐个断开或屏蔽GPS、IMU、视觉、雷达 | 失效模态不可用，其他模态继续工作 |

所有动态场景先低速完成。目标由远及近时，使用受控推行目标或固定路线，禁止把“接近碰撞”作为测试终点。

## 6. IMU标定步骤

IMU优先标定，因为正常转弯补偿错误会污染后续综合风险观察。

精调IMU时先停止Dashboard，单独运行100 Hz原始数据采集工具，避免两个进程同时打开IMU串口：

```bash
python scripts/record_imu_validation.py \
  --profile dk2500 \
  --scenes static,push_straight,normal_turn,stop \
  --output-dir runs/imu_validation/vehicle_round_01
```

不同速度或转弯半径使用不同输出目录重复采集。Dashboard录制仍用于观察整机风险和时间对齐，但不能代替这份100 Hz IMU原始数据。

### 6.1 标定静止零偏

1. 车辆按最终安装状态直立固定，静止60秒。
2. 计算`roll`均值或中位数，作为新的`roll_offset_deg`候选。
3. 记录静止波动P95/P99。
4. 左右各重新扶正一次并重复，三个结果差异明显时先检查安装松动，不调阈值。

保留条件：修正后的`body_roll=roll-roll0`在三次静止测试中都接近0，且左右没有固定偏置。

### 6.2 验证转弯方向

1. 分别完成稳定左转和右转。
2. 检查左转`gyro_z`与左倾`roll`、右转`gyro_z`与右倾`roll`的符号。
3. 检查`phi_eq=turn_sign*atan(v*yaw_rate/g)`是否与实际车身倾斜同向。
4. 当前`turn_sign=-1`。如果左右两侧都被补偿得更差，先核对轴方向，再考虑改为`+1`。

不得根据一次转弯修改符号。至少两种速度、左右各3次结果一致才保留。

### 6.3 中风险初值

当前条件：

```text
|roll_error| >= 10°
outward_rate >= 5°/s
持续 >= 150 ms
```

调整顺序：

1. 先固定速度阈值和持续时间，只比较`attention_error_deg`。
2. 建议围绕当前值做局部候选：`8° / 10° / 12°`。
3. 普通转弯误报多就增大；安全可控快速侧倾报警太晚就减小。
4. 选定角度后再比较`attention_outward_rate_deg_s`：`3 / 5 / 7°/s`。
5. 最后比较`attention_persistence_ms`：`100 / 150 / 200 ms`。

保留条件：普通转弯和颠簸不持续触发中风险，同时快速外倾能在人工开始扶正之前触发。

### 6.4 高风险初值

当前条件：

```text
临界残差 = 25°
当前残差 >= 8°
outward_rate >= 10°/s
预计0.8 s内达到临界残差
连续3个有效样本
```

只按以下顺序调：

1. 先保持`critical_error_deg=25°`，比较`prediction_horizon_s=0.6/0.8/1.0 s`。
2. 高风险太晚时增大预测时间；正常快速转弯误报时减小。
3. 再比较`urgent_outward_rate_deg_s=8/10/12°/s`。
4. 最后才比较`critical_error_deg=20/25/30°`。
5. 第一轮保留连续3样本，不先修改一致性帧数。

高风险必须在达到临界残差前首次触发。已经严重倾斜或倒地后才触发不算成功预警。

### 6.5 GPS不可用检查

GPS无效或速度低于转弯补偿最低速度时，IMU当前最高限制为中风险。验证这时：

- 正常低速转弯不会频繁误报高风险。
- 雷达和视觉高风险仍可正常输出。
- Dashboard显示IMU补偿降级，而不是显示正常补偿。

## 7. 视觉标定步骤

### 7.1 先标定走廊，不先调tau

1. 在地面中心和路径左右边缘放置明显标记。
2. 采集直道、宽路、窄路和缓弯画面。
3. 检查当前梯形顶部`0.40H/0.10W`、底部`0.50W`是否覆盖实际前向行驶路径。
4. 走廊过宽导致路边误报就收窄；漏掉真实切入路径的目标就放宽。
5. 道路宽度不能直接等同于画面宽度比例；这里标定的是车辆未来行驶区域在图像中的投影。

### 7.2 比较路径点策略

使用同一组S05、S06场景，分别测试：

```text
center
two_of_three
any
```

- `center`最严格，路边误报少，但可能漏掉刚切入的目标。
- `two_of_three`是折中。
- `any`召回最高，但最容易把路边目标判为路径障碍。

选择原则：危险切入场景不得漏报，在此前提下选择路边误报最少的方案。

### 7.3 再调远近位置与视觉tau

只有检测框稳定、走廊正确后才进行：

1. 正前目标由远及近，记录框底部`y2/H`和首次人工认为需要注意的时刻。
2. `near_bottom_ratio`过小会过早进入中风险，过大则报警晚。
3. `very_near_bottom_ratio`只调整非常近的单帧位置参考，不能代替视觉tau。
4. 视觉跟踪稳定后，再比较`attention_tau_s`和`urgent_tau_s`。
5. 视觉高风险太晚就增大对应tau参考；误报太早就减小。

每次只改一个比例或一个tau值。检测框频繁换轨时，先修关联稳定性，不用风险阈值掩盖。

## 8. 雷达标定步骤

### 8.1 横向point gate

固定TTC参数，按顺序测试：

```text
0.015 m
0.025 m
0.035 m
```

- S06路边目标误报多：尝试减小。
- S05路径边缘目标漏报：尝试增大。
- 正前目标和路径边缘目标不得因缩小门限而漏掉高风险。

三组候选都不理想时，先检查雷达安装偏移、角度符号和车体宽度，不继续扩大搜索范围。

### 8.2 TTC提前量

先固定point gate，再测试：

```text
urgent_reference_s = 2.0 / 2.5 / 3.0 s
```

- 高风险提醒太晚：增大。
- 高风险持续过早、正常跟车误报：减小。
- 受控危险场景首次进入高风险后，升级不得被平滑或保持逻辑延迟。

`urgent_reference_s`只能描述“反应时间紧迫参考”，不得称为完整制动安全时间。

中风险确实明显不合理时，再围绕`attention_reference_s=4.0 s`做局部测试，并始终保持：

```text
attention_reference_s > urgent_reference_s
```

## 9. GPS、时效与下降保持

### 9.1 GPS速度修正最后再调

GPS只修正缺少可靠tau的视觉单帧接近风险，不改变雷达TTC和视觉tau。

1. 先确保GPS静止时不会长期输出明显非零速度。
2. 对同一视觉场景用低、中、高速通过，观察视觉分数是否随速度温和上升。
3. 如果高速视觉明显低估，可小幅增大`max_factor`；误报增多则减小。
4. 第一轮不建议超过当前`1.25`，也不引入GPS制动时间。

### 9.2 stale参数只能由统计得到

分别统计每个模态的有效样本间隔和线程排队延迟P50/P95/P99。候选时效窗口至少覆盖：

```text
P99有效更新间隔 + P99线程排队延迟 + 工程余量
```

然后验证：

- 健康设备不会频繁被判`stale`。
- 真实拔线或停更后能及时进入`stale/unavailable`。
- 过期数据不能继续维持新的低风险或高风险判断。

不得仅凭感觉修改`target_stale_ms`、`vision_stale_ms`、`imu_stale_ms`和通信看门狗。

### 9.3 release hold最后调

候选值：

```text
300 / 500 / 700 ms
```

- 同一事件频繁`0→1→0→1`：增大。
- 危险解除后保持过久：减小。
- 每个候选都要确认风险升级仍立即生效。

## 10. 每轮现场操作模板

每一个候选参数都执行以下完整循环：

1. 从基线复制一份候选YAML。
2. 修改`version`，例如`vehicle-imu-attention-8deg-v1`。
3. 只改一个参数。
4. 运行配置和相关规则测试。
5. 启动Dashboard并使用独立`--scene`录制。
6. 固定路线和速度，重复对应场景3至5次。
7. 运行录制质量检查。
8. 填写第11节记录表。
9. 与基线比较误报、漏报、首次报警时刻和抖动。
10. 明确写“保留”或“回退”，再开始下一个参数。

配置修改后的最低软件回归：

```bash
python scripts/test_warning_config.py
python scripts/test_imu_warning_rule.py
python scripts/test_competition_risk_rule.py
python scripts/test_multimodal_warning_system.py
python scripts/test_warning_scenario_matrix.py
python scripts/test_warning_session_replay.py
```

## 12. 第一轮验收标准

- 所有受控危险场景不得漏掉可用雷达高风险事件。
- 高风险进入边界后立即升级，不等待视觉、GPS、IMU或下降保持。
- 空旷直道和普通转弯不出现持续高风险。
- GPS、IMU、视觉或雷达单独失效时，其他模态继续工作。
- 全部核心预警模态不可用时输出`unknown`，不能显示正常低风险。
- 同一事件不频繁出现`0→1→0→1`。
- 每个风险证据满足`采集时间 <= 完成时间 <= 决策时间`。
- Dashboard状态循环启用IMU时实际频率应稳定接近20 Hz；持续低于18 Hz时先排查性能，不继续调阈值。
- 修改后现有配置、规则、融合、Dashboard录制和回放测试继续通过。

## 13. 推荐的最简执行顺序

如果现场时间有限，只完成下面七步：

1. 核对雷达APP范围，完成硬件预检。
2. 测IMU静止零偏和左右转弯方向。
3. 建立S01至S06基线，每项3次。
4. 比较视觉`center`与`two_of_three`。
