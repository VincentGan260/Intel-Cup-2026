# 整机端到端延迟测试方案

## 1. 测试目标

本测试不测量振动马达的机械起振时间，也不测量振动传递到佩戴者头部的时间。

本项目统一使用以下工程口径：

> 传感器关键样本产生或到达主机，到 DRV2605 `GO` 指令写入完成的时间。

该指标命名为：

> 整机感知到执行指令延迟。

它应覆盖真实传感器读取、视觉推理、风险规则、多模态仲裁和电机控制，但不包含传感器内部扫描发生前的物理过程，也不包含马达机械响应。

## 2. 分模态测量口径

不同传感器采样频率和处理链路不同，不能把所有样本直接混合后计算一个平均值。必须分别统计雷达、视觉和 IMU 三条触发链路。

| 触发模态 | 起点 | 终点 |
|---|---|---|
| 雷达 | LD2451 数据到达 DK2500 主机的单调时钟时间 | DRV2605 `GO` 写入完成 |
| 视觉 | 触发风险的摄像头帧采集时间 | DRV2605 `GO` 写入完成 |
| IMU | 触发风险的 WT61C 数据到达主机时间 | DRV2605 `GO` 写入完成 |

GPS 只提供速度上下文，不独立产生预警，因此不单独统计 GPS 到电机的延迟。

每条链路分别输出：

- 有效样本数；
- 平均值；
- P50；
- P95；
- P99；
- 最大值；
- 无效样本数及无效原因。

整机最终指标采用：

> 雷达、视觉和 IMU 三条触发链路中最大的 P95。

报告中必须同时保留三条链路的独立结果，不能只展示这个最大值。

## 3. 单次延迟记录

每次真实写入 `GO` 时只生成一条记录。建议 JSONL 结构如下：

```json
{
  "trigger_source": "vision",
  "supporting_sources": ["radar"],
  "trigger_level": 1,
  "sensor_capture_monotonic_ns": 1000000000,
  "rule_completed_monotonic_ns": 1098000000,
  "decision_monotonic_ns": 1099500000,
  "motor_go_monotonic_ns": 1100000000,
  "sensor_to_rule_ms": 98.0,
  "rule_to_decision_ms": 1.5,
  "decision_to_go_ms": 0.5,
  "e2e_latency_ms": 100.0,
  "motor_actual": "real"
}
```

各分段定义：

```text
sensor_to_rule_ms
  = rule_completed_monotonic_ns - sensor_capture_monotonic_ns

rule_to_decision_ms
  = decision_monotonic_ns - rule_completed_monotonic_ns

decision_to_go_ms
  = motor_go_monotonic_ns - decision_monotonic_ns

e2e_latency_ms
  = motor_go_monotonic_ns - sensor_capture_monotonic_ns
```

分段结果用于定位延迟来源：

- `sensor_to_rule_ms` 高：检查传感器读取、视觉推理或规则处理；
- `rule_to_decision_ms` 高：检查多模态仲裁和线程调度；
- `decision_to_go_ms` 高：检查电机控制、I2C 和控制器锁等待；
- `e2e_latency_ms` 高：检查整条触发链路。

## 4. 触发归属规则

只有真正导致电机启动的风险升级才构成延迟样本。

1. 只记录风险等级从未知或低风险升级到中风险或高风险，并实际写入 `GO` 的事件。
2. 同一等级的重复传感器数据不重复统计，因为电机没有重新启动。
3. 雷达高风险快速通道单独标记为 `radar-fast`，但汇总时同时并入雷达链路。
4. 多个模态同时有效时，以真正导致本次等级升级的最新模态作为 `trigger_source`。
5. 其他有效模态只记录为 `supporting_sources`，不得为同一次 `GO` 重复生成样本。
6. 风险降级、解除保持和停止振动不纳入预警启动延迟。
7. 同一传感器缓存样本不得重复统计。
8. 时间戳缺失、倒序或来自未来的样本必须剔除。
9. 电机实际降级为 mock 时，该轮只能用于验证程序，不得进入正式结果。
10. 正式分析必须确认每条记录的 `motor_actual` 为 `real`。

## 5. 算法确认时间说明

本方案的主指标从“最终触发风险的关键样本”开始计时。

IMU 连续样本确认、视觉跨帧跟踪等算法可能在关键样本之前已经积累证据。这部分属于规则设计产生的确认时间，不应和单次软件处理延迟混为一谈。

如后续需要评估“危险趋势首次出现到发出预警”的响应时间，应增加独立指标：

```text
condition_start_to_go_ms
```

该指标需要各规则额外暴露证据窗口开始时间。第一轮整机测试暂不将它作为主指标，避免不同模态的判定机制混算。

## 6. 正式测试前需要实现的代码

以下功能目前尚未全部实现，完成后才能按本方案正式采集整机数据。

### 6.1 电机调度记录

在 `TimedMotorController` 中保存每次真实 `GO` 写入记录：

- 唯一调度序号；
- 风险等级；
- `GO` 写入完成的单调时钟时间；
- 是否真实电机；
- 写入是否成功。

必须生成不可变的单次记录，不能只读取一个可能被后续命令覆盖的共享时间戳。

### 6.2 风险升级与触发源关联

在 `WarningState` 和 `MultimodalWarningSystem` 中建立以下关联：

```text
传感器事件
-> 仲裁结果
-> 风险状态升级
-> 电机GO记录
```

雷达快速通道必须保留现有优先行为，延迟埋点不能让它等待视觉或普通仲裁。

### 6.3 多模态延迟记录器

新增多模态延迟记录器，负责：

- 按调度序号去重；
- 校验时间戳顺序；
- 记录触发源和辅助证据；
- 写入 JSONL；
- 标记 mock、丢失时间戳和异常顺序；
- 关闭程序时输出样本计数。

### 6.4 Dashboard 参数

计划增加：

```text
--e2e-latency-log PATH
--overwrite-e2e-latency-log
```

在这些参数完成前，下面的正式命令不能直接使用。

### 6.5 分析脚本

新增整机分析脚本，按以下类别输出统计：

```text
radar
radar-fast
vision
imu
overall-worst-p95
```

分析脚本必须拒绝把 mock 记录混入正式结果，并报告被剔除的样本数量和原因。

## 7. DK2500 主机测试准备

### 7.1 固定测试条件

- 摄像头、雷达、IMU 和马达使用最终安装位置；
- 测试期间不得改变传感器角度、接口或固定方式；
- DK2500 接通电源并使用统一性能模式；
- 记录 OpenVINO 版本、驱动版本和设备温度；
- 关闭无关后台程序和浏览器标签页；
- LD2451 APP 检测范围必须与系统配置一致；
- 正式测试必须使用真实传感器和真实电机。

### 7.2 硬件预检

在项目根目录运行：

```bash
python scripts/preflight_dk2500.py --profile dk2500 --loops 30 --vision
```

确认：

- 雷达持续产生合法帧；
- 摄像头帧号和采集时间持续更新；
- IMU 持续产生有效样本；
- NPU 检测和 GPU 分割均使用预期设备；
- DRV2605 可以真实驱动；
- 时间戳不存在倒序、未来时间或持续停滞。

## 8. 计划使用的启动命令

完成第 6 节的代码后，计划使用：

```bash
python run_dashboard.py \
  --dashboard-mode real \
  --profile dk2500 \
  --enable-risk-rule \
  --enable-vision \
  --enable-imu \
  --motor-mode real \
  --confirm-motor-real \
  --e2e-latency-log logs/system_e2e_latency.jsonl \
  --overwrite-e2e-latency-log
```

还需要按 LD2451 APP 的实际配置传入正确的：

```text
--configured-warning-range-m
```

第一轮可使用 mock 电机检查日志结构，但 mock 结果不能用于正式结论。

## 9. 受控测试场景

### 9.1 雷达触发

条件：

- 正前方目标受控接近；
- 视觉和 IMU 保持低风险；
- 每轮从低风险状态开始。

检查：

- `trigger_source` 为 `radar` 或 `radar-fast`；
- 高风险快速通道没有等待视觉；
- 雷达样本时间早于规则完成、决策和 `GO` 时间。

### 9.2 视觉触发

条件：

- 静态障碍物进入视觉骑行路径；
- 雷达不形成动态高风险；
- IMU 保持稳定。

检查：

- `trigger_source` 为 `vision`；
- 起点使用触发风险的摄像头帧采集时间；
- 延迟包含检测、分割、视觉规则、仲裁和电机控制。

### 9.3 IMU 触发

条件：

- 车辆固定在保护架或由专人扶稳；
- 前方没有障碍物；
- 进行受控侧倾，禁止高速和无人保护测试。

检查：

- `trigger_source` 为 `imu`；
- 使用触发风险的 IMU 主机接收时间；
- 正常转弯补偿不能污染正式触发样本。

### 9.4 多模态触发

条件：

- 目标接近并进入视觉路径；
- 保持 IMU 稳定；
- 使用同一受控路线重复测试。

检查：

- 同一次 `GO` 只记录一次；
- 主要触发源和辅助证据清楚；
- 雷达高风险快速通道仍然优先；
- 不把多个旧传感器时间戳分别计算成多条延迟。

## 10. 样本量和测试节奏

1. 正式记录前预热至少 30 秒。
2. 丢弃每个测试阶段最初 10 次触发。
3. 每个模态至少采集 100 次有效触发。
4. 每次触发后等待风险恢复为低风险，再开始下一次。
5. 确认上一轮电机状态已经解除。
6. 测试中途改变配置、硬件位置或系统性能模式后，必须重新开始该组。
7. 测试期间记录温度异常、后台任务和设备重连事件。

少于 30 个样本只能用于初步排错，不应作为正式 P95 结论。

## 11. 数据质量判据

正式结果至少满足：

- `motor_actual=real`；
- 三类模态均达到要求的有效样本数；
- 时间戳严格满足：

```text
sensor_capture <= rule_completed <= decision <= motor_go
```

- 没有重复调度序号；
- 没有同一传感器样本重复计数；
- 没有负延迟；
- 设备重连期间的异常样本被明确标记或剔除；
- `radar-fast` 没有被视觉处理阻塞；
- 原始 JSONL、汇总结果和运行配置一同保存。

暂不提前写死未经实测支持的绝对达标阈值。第一次正式结果作为 DK2500 基线，后续修改只有在相同条件下稳定改善 P95 且不增加错误率时才保留。

## 12. 现有工具的限制

当前 `measure_dk2500_p95.py` 使用：

```text
--latency-only
--force-alert-level 2
```

它会跳过视觉并强制触发二级预警，适合验证：

- 雷达主机接收到 DRV2605 `GO` 的快速链路；
- I2C 和真实电机是否可用；
- 雷达快速通道的 P95。

它不能作为视觉、雷达和 IMU 全部参与的整机端到端结果。

## 13. 最终输出

正式测试完成后应保留：

1. 原始 `system_e2e_latency.jsonl`；
2. 分模态统计 JSON；
3. 一页汇总表；
4. DK2500、OpenVINO、驱动和性能模式信息；
5. 测试场景、样本数和异常说明；
6. 本次使用的 Git commit 和风险规则配置副本。

答辩建议使用以下表述：

> 系统端到端延迟按感知样本到 DRV2605 启动指令定义，在 DK2500 实机上分别测量雷达、视觉和 IMU 链路，并以三条链路中最大的 P95 表示整机最坏典型响应延迟。该指标不包含振动马达机械起振时间。
