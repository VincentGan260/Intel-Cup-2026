模型性能测试方案讨论要点总结
背景
•	载体:电动车(非机动车),非汽车。
•	目标:检测障碍物(人 + 各类车),用于生成视觉风险;类别能分最好,分不清也可接受。
核心决策(含理由)
1. 分割:测「整片路面 road」,不测「可行驶区域 drivable」
•	电动车不走汽车车道,汽车的 drivable(车道级)定义不适用;
•	"整片路面"更接近电动车可骑行的地面;
•	现有模型(road-adas / PIDNet)本就输出整片路面,且 road 类有干净 GT,IoU 评测公平。
2. 检测:只做「类别无关的障碍物检测」,不分人/车
•	对电动车,撞人 vs 撞车风险无法分高低,故不区分;
•	风险主要由几何决定(距离、是否挡路、目标大小),类别非主因;
•	模型(nano + 域差)分类不可靠,依赖类别会脆弱;
•	评测时两边都先筛出"障碍物"类(人+各类车,排除 traffic light/sign/train),再不分类按 IoU 匹配 → 顺带规避了 COCO↔BDD 编号对齐问题。
3. 评测对象:OpenVINO FP32
•	PyTorch FP32 ≈ OpenVINO FP32(精度等同),只对 PyTorch 做一次性一致性抽查确认导出无误;
•	跳过 FP16(精度等同 FP32,无独立价值,归端侧速度轮);
•	精度的真正权衡 = FP32 vs INT8,留给量化轮;速度/设备对比归端侧轮。
4. 指标引擎用 torchmetrics
•	手写 mAP 易错(队友旧版已出 bug),用公认正确的库算,既对又省事。
5. 分割 GT:混多个数据集(Cityscapes + 其他)
•	体现跨天气/场景泛化;
•	架构 = 1 套共享核心 + 每数据集一个小适配器(说明路径、格式、哪个值=road);
•	易错点是"标签约定"(trainId vs labelId、ignore、最近邻缩放),这部分由我兜底/核对。
检测精度指标(及优先级)
"@0.5" = 预测框与真值框重叠 ≥50% 才算命中。
优先级	指标	含义
🥇	Recall@0.5	障碍物被检出的比例;漏检=安全命门,最重要
🥇	按目标尺寸拆(小/中/大)	诊断"多远能检到",nano 小目标短板
🥈	Precision@0.5	报出的框中真障碍占比;控误报,影响可用性
🥉	mAP@0.5	跨置信度综合分;模型间横向对比用
🥉	mAP@0.5:0.95	更严(奖励框贴合精度);对避障最不关键,凑齐即可
分割精度指标
•	主:road IoU(road-adas vs PIDNet-S 公平对比);
•	多类模型可另算 mIoU,但主看 road;
•	像素准确率弱化,且须在同一标签空间下算(旧脚本跨编号 == 要改)。
待办(卡点)
•	⏳ 队友确认 BDD 检测标注格式(旧版逐图 json frames[].objects[].box2d )→ 确认后即可写检测评测(也可两种格式都兼容,不等)。









端侧延迟测试 · 全套流程
0. 目标 & 前提
目标:在 DK-2500 上量出各配置的真实速度,回答"能不能实时、哪个配置最划算"。
前提清单(齐了才能测):
•	硬件:DK-2500(Core Ultra 5 225U,设备有 CPU / iGPU / NPU)
•	系统:Ubuntu + OpenVINO(建议装好 NPU 驱动)
•	模型:每个模型都要有 FP32 / FP16 / INT8 三个版本(由精度轮的量化产出)
•	固定测试输入:一段固定的图/短视频(所有配置用同一份,保证可比)
关键认知:延迟必须在这块板子上测,开发机的速度数对比赛无意义。
1. 测什么(指标)
指标	定义	为什么要
纯推理延迟	只算模型前向那一下	定位模型本身快慢、做设备/精度对比
端到端延迟	含预处理+推理+后处理	决定实时的是这个,不是只看前向
延迟分布(均值/中位/p95)	多次测量的统计	p95 最该看——偶发卡顿才是实时杀手
FPS / 吞吐	每秒处理帧数	直观实时能力
管线总延迟(检测+分割并行)	两模型并发后整体耗时	你们要并行,这才是系统真实速度
内存占用	推理时峰值 RAM	端侧 16GB 受限,确认放得下
模型体积	IR 大小	存储 + 加载时间参考
(可选)温度/降频	长时间跑后是否掉速	看持续实时能力
口径统一:都用 batch=1(实时单帧)、丢掉热身、报稳态。
2. 测哪些配置(对比矩阵)
不做全排列(太多),分两阶段聚焦:
阶段 A — 每个模型,找它的最佳"精度×设备"
模型	要测的组合
检测 yolo26n	CPU-FP32、CPU-INT8、iGPU-FP16、iGPU-INT8、NPU-INT8
分割 PIDNet-S	同上 5 组
(基线)road-adas	CPU-FP32、iGPU-FP16、NPU-INT8(对照)
说明:NPU 基本只吃 INT8;FP16 在 iGPU 上最有意义;CPU-FP32 是基线。所以不是每格都测,按上面这份就够。
阶段 B — 把检测+分割合起来,找最佳并行摆放
用阶段 A 各自的最优设备,测并发:
•	检测→NPU + 分割→iGPU
•	检测→iGPU + 分割→NPU
•	两个都→CPU(对照)
•	…(挑 3~4 种合理组合)
判据:总延迟 ≈ max(检测, 分割) 的那种摆放最好;必须测真实并发数(同时跑会抢资源,不能拿单独的数相加)。
3. 怎么测(正确方法 · 步骤)
每个配置都按这套走:
1.	固定输入:同一份图/视频,batch=1,固定分辨率。
2.	预热:先空跑 10~20 次,丢掉(第一次加载/编译特别慢)。
3.	稳态测量:连续跑 ≥100 次(或固定 30 秒),逐次记录耗时。
4.	统计:算 均值 / 中位 / p95 / 最大,不要只报均值。
5.	分段计时:分别量"纯推理"和"端到端"(在预处理前、推理前后、后处理后打时间戳)。
6.	同步模式测延迟:实时场景用同步单帧(latency 模式);吞吐(async 多路)另测,别和延迟混。
7.	并发测量(阶段 B):两模型各绑定设备同时跑,量整体每帧延迟。
8.	记录环境:设备、精度、OpenVINO 版本、电源模式(设成 performance)、是否插电、跑前温度——这些都影响数,必须随数记。
工具:
•	benchmark_app(OpenVINO 自带):快速出"纯推理"的延迟/吞吐,适合阶段 A 批量扫。
•	自写管线计时脚本:出"端到端 + 并发"的真实数,适合阶段 B 和最终系统数。
4. 判定标准(达标线)
•	整环 ≥ 10 FPS(≤100 ms) = 实时地板线;
•	视觉(检测+分割并行)≤ 65 ms ≈ 15 FPS 为目标;
•	风险评分 + 马达单独量一次,确认很轻(预计几 ms);
•	最终选**同时满足"精度够"(精度轮)+ "延迟达标"**的那个配置。
5. 最终产物
1.	延迟总表:每配置一行(模型/精度/设备/均值/p95/FPS/内存/体积)。
2.	精度 × 延迟 散点图:把精度轮的数合进来,一眼挑部署配置。
3.	一句话推荐:例如"检测 NPU-INT8 + 分割 iGPU-FP16,并行整环 ~X ms,达标"。
6. 容易踩的坑(提前规避)
•	散热降频:短时快 ≠ 持续快。要长时间连续跑看会不会掉速。
•	电源/省电模式:Ubuntu 默认可能降频,测前设 performance、确认插电。
•	后台干扰:关掉无关进程,否则数飘。
•	并发要测真数:别用"单独跑的数相加"近似并行。
•	端到端别漏预处理:resize/归一化/argmax 这些也算进去。
•	首次加载慢:务必预热后再测。
•	NPU 限制:NPU 偏好 INT8 + 静态输入形状,FP32 不一定能跑——所以 NPU 主要测 INT8。
